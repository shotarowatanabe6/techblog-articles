## 各トピックの狙い

学習の目的は「コマンドの使い方」ではなく「なぜそう動くか」。エンジニア6年目・pull/commit/push は日常的に使えている前提なので、基本操作の説明はしない。

### 第1部: Gitが保存しているもの（土台）

- **1. オブジェクトモデル** — `git hash-object` / `git cat-file` でオブジェクトを手で作り、blob→tree→commit の参照関係を組み立てる。「コミットは差分ではなくスナップショット」を実物で確認する
- **2. 参照とHEAD** — `.git/refs/heads/` の中身がただの40文字であることを見る。detached HEAD を意図的に作って戻す。ブランチが「軽い」理由をここで腹落ちさせる
- **3. インデックス** — `git ls-files -s` で中身を覗く。`add` が何をしているのか。**HEAD / index / 作業ツリーの3つのツリー**という枠組みをここで導入し、以降の説明の共通言語にする

### 第2部: 履歴を動かす

- **4. reset の3モード** — 「3つのツリーのどこまで動かすか」で統一的に説明する。`checkout` / `switch` / `restore` との棲み分けも同じ枠組みで整理
- **5. merge と rebase** — fast-forward と 3-way の違い。rebase がコミットを**作り直している**（ハッシュが変わる）ことをログで確認する
- **6. コンフリクト** — 競合中の index に stage 1/2/3 が並ぶのを `git ls-files -u` で見る。「なぜ手で直して `add` すると解決になるのか」
- **7. 履歴の整理** — `rebase -i` の squash / fixup / reword、`cherry-pick`、`revert`。レビュー前のコミット整理という実務文脈で。**軽めでよい**（記事では独立章にせず3章・5章に分散させる）

### 第3部: 壊してから直す（事故対応）

- **8. reflog** — `reset --hard` で消した / ブランチを消した / rebase に失敗した、の3パターンを**自分で起こして自分で戻す**
- **9. push 後の巻き戻し** — revert と force push の使い分け。`--force-with-lease` が具体的に何を守っているか（他人のpushを上書きする事故を再現する）

### 第4部: リモート

- **10. fetch / pull / push** — remote-tracking branch（`refs/remotes/origin/*`）の実体。`pull` = fetch + merge/rebase。`pull.rebase` をどう設定すべきか
